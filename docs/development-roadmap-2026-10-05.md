# lawCheck 개발 우선순위와 작업 목록

조사일: 2026-10-05. 기준은 현재 작업 트리, [MVP 기획서 v0.4](legal_ai_platform_solution_plan_v0.4.md), [README](../README.md), 기존 [후속 작업 목록](future-work.md)이다. 이 문서는 조사 결과이며 기능 완료 판정은 각 작업의 검증과 데이터 보존 확인 후 내린다.

## 현재 상태

- FO에는 익명 브라우저 쿠키, 대화 저장·목록·화면 복원, 음성 입력, 질문별 검증 요청과 답변 조회가 있다.
- API에는 Prisma migration, 질문 저장, OpenAI 응답, 검증 게시판, 전문가 로그인, 관리자 기능, 답변 이메일 큐·재시도 기능이 있다.
- BO는 가입·로그인, 검증 게시판, 커뮤니티 중심이다. MVP 기획서의 사무실별 직원 권한, 변호사 인력·휴가, 단일 담당자 배정·재배정 흐름과는 다르다.
- `docs/future-work.md`와 README의 일부 설명은 현재 코드보다 오래되었다. 예를 들어 FO 복원과 실제 검증 요청이 아직 연결되지 않았다고 설명하지만 현재 코드에는 해당 경로가 있다. 문서를 완료 증거로 사용하지 말고 실제 API와 테스트로 판정해야 한다.
- 이메일 HTML 발송, 질문 `requestKey`, 검증 대상 제한을 구현하고 API·브라우저 테스트로 검증했다. 서버 중단 후 같은 키로 재요청해도 실패 상태와 질문 횟수 복구가 DB에 반영된다.

## 2026-10-05 구현·운영 배포 기록

- 이번 범위는 P0 안정화와 P1의 검증 요청 조건 강화다. 기존 다중 전문가 답변 방식과 이메일 대화 복원 정책을 유지한다.
- 완료 답변 재사용, 같은 키의 다른 질문 거절, 처리 중·실패·서버 중단 복구, 새 프로세스의 기존 답변 재사용을 DB 통합 테스트로 확인했다. FO의 임시 대화에서 서버 세션 ID로 전환, 네트워크 재시도, 실패 후 새 키, 새 대화 전환도 확인했다.
- 검증 요청은 소유한 대화의 완료된 `AI_ANSWER`만 허용한다. 같은 이메일의 중복 요청은 기존 요청을 반환하며 다른 이메일이면 409로 거절하고 기존 주소를 보존한다.
- 이메일은 질문·전문가 답변을 이스케이프한 HTML과 텍스트 대체 본문을 함께 발송한다. 로컬 SMTP 수신과 Resend 요청, 갱신된 링크, 긴 답변 보존을 테스트했다.
- 검증: `npm test` 33개 통과, `npm run typecheck`, `npm run lint`, 전체 빌드 통과. E2E 70개 중 68개 통과 후 오래된 관리자 메뉴 기대값을 수정하고 해당 파일의 데스크톱·모바일 6개를 재실행해 모두 통과했다. `npm run test:db`의 19개 migration과 35개 테이블 무결성 검증도 통과했다.
- E2E가 다른 프로젝트의 5173 포트 서버를 재사용하던 문제를 수정했다. FO 테스트 포트는 15173이며 기존 서버를 자동 재사용하지 않는다.
- 운영 PostgreSQL custom-format 백업을 `backups/lawcheck-production-20261005-predeploy.dump`에 보관하고 별도 PostgreSQL 18에 복원했다. 운영에 적용된 migration 19개의 SQL 내용이 저장소와 일치한다. 기존 세션 159건, 메시지 112건, 검증 요청 16건, 전문가 기여 7건, 이메일 2건, 발송 시도 2건의 ID·행 해시를 비교 기준으로 보관했다. 백업과 행 해시는 Git에서 제외한다.
- 이번 변경은 기존 `request_key` 컬럼과 유일 제약을 사용하므로 새 migration이 필요하지 않다.
- 운영 반영 커밋: `dab9774e802c9a6448cf7efc5bfd93f24f66329f` (`master`). Railway `AI-Qaver / production`의 API 배포 `1f99d875-b4a6-4731-9f6c-3626171aee41`, FO 배포 `f8d48db8-7a45-47f4-9534-6bbae76f969f` 모두 `SUCCESS`를 확인했다. API 사전 배포 로그는 적용할 migration이 없고 기존 데이터·비밀번호를 보존한 seed가 완료됐음을 확인했다.
- 배포 후 운영 DB에서 기준 기록 298건의 ID와 전체 행 해시를 비교해 누락 0건·변경 0건을 확인했다. 당시 추가된 1건은 운영 화면 검증 과정에서 생성한 빈 대화 세션이다. 이후 모바일 확인에서도 빈 세션이 추가되며 질문·이메일은 생성하지 않았다. Prisma DB 검사에서 35개 테이블·논리 스키마 주석·사무실 설정이 정상임을 확인했다.
- `api.aiqaver.com`과 FO·BO·Admin의 `/api/v1/health`가 모두 200을 반환했다. FO 경유 잘못된 `requestKey`는 400 `INVALID_QUESTION`으로 거절됐다. 운영 FO의 새 번들 `/assets/index-DdowXA9u.js`, 실제 DB 대화 조회, Secure·HttpOnly·SameSite=Strict 쿠키, 데스크톱·모바일 표시와 모바일 메뉴 열기를 확인했다.
- 운영에서 실제 AI 질문과 수신자 이메일 발송은 실행하지 않았다. AI·이메일 성공/실패·재시도는 격리 API 테스트와 로컬 SMTP/Resend 어댑터 테스트 범위에서 검증했다. 이메일 링크 권한 재설계와 사무실별 배정·권한 모델은 아래 후속 작업으로 남는다.
- 이전 정상 배포는 API `36ebf548-5302-45bc-a7db-3e5ca8b5c4e9`, FO `957becef-d7b2-4de2-a6a3-17d1e771c172`이며 이전 커밋은 `9ea025e148b2e13785c12ebe86bc0117a2833f00`이다. 백업 SHA-256은 `0f015e1d75e78f358209bd448fe36d855c0c113e00308ca4511d8f77de03878e`이다.

## P0 — 현재 변경 검증과 데이터 보존 기준

1. **완료: 미완료 변경 검증.** 이메일 HTML 이스케이프·텍스트 대체 본문·SMTP/Resend 처리, 질문 `requestKey` 완료 응답 재사용·처리 중·실패·동시 요청을 API 테스트로 확인했다. 재전송 때 질문·답변·사용 횟수가 늘지 않으며 FO의 `draft`에서 서버 세션 ID로 전환하는 경우도 검증했다.
2. **완료: 이번 배포의 기존 기록 보존.** 격리 DB에서 migration·무결성·재시작 후 대화 복원을 검증했고, 운영 백업을 별도 PostgreSQL에 복원했다. 운영 배포 전후 기존 기록 298건의 ID·전체 행 해시가 동일함을 확인했다. 이후 DB 변경에도 같은 기준으로 백업·복원·보존 검증을 반복한다.
3. **완료: 검증 환경 회복.** 이번 실행에서 기존 `uv_os_get_passwd: ENOMEM`은 재현되지 않았고 API 테스트 33개가 통과했다. E2E 서버 재사용 문제를 수정하고 타입 검사·lint·빌드와 데스크톱·모바일 테스트를 실행했다.

## P1 — 공개 흐름의 접근 제어와 업무 모델

4. **완료: 검증 요청 대상 조건 강화.** `POST /reviews`에서 소유 세션·완료 상태·`AI_ANSWER`를 검사한다. 같은 이메일의 중복 요청은 기존 요청을 반환하고 이메일을 바꾼 재요청은 409로 거절한다. 비법률 답변과 타인 답변 접근 거절을 DB 통합 테스트로 확인했다.
5. **답변 링크 권한을 정리한다.** 현재 이메일의 답변 링크는 답변 조회 외에 그 질문의 전체 대화를 새 브라우저로 복원할 수 있다. 기획서의 질문별 최소 공개 원칙과 맞춰 링크가 노출할 데이터와 이어서 질문할 권한을 확정하고, 토큰 만료·재사용·공유·타 세션 접근 테스트를 작성한다.
6. **BO를 사무실별 담당자 업무로 연결한다.** 현재 게시판은 여러 전문가가 같은 질문을 각각 `claim`하고 답변하는 구조다. MVP 기획서는 사무실 내 적격 변호사 한 명의 배정·재배정·회수를 요구한다. 기존 `VerificationRequest`, `ReviewInvitation`, `AssignmentHistory`, `LawyerReply`, `EmailOutbox` 스키마와 현재 `ReviewBoardPost` 데이터를 어떻게 연결·이관할지 먼저 설계하고 migration을 작성한다. 기존 답변과 발송 이력은 삭제하지 않는다.
7. **직원 권한과 변호사 적격성을 구현한다.** 사무실별 직원 로그인·역할, 변호사 승인·활성 상태·입퇴사·휴가를 배정과 답변 API에서 검사한다. 계정 정지·퇴사·재배정 시 기존 세션과 링크를 차단하고 감사 이력을 남긴다.

## P2 — 발송 신뢰성, 개인정보와 운영

8. **배정 초대와 사용자 답변 발송을 일관된 큐로 관리한다.** DB 저장과 발송 예약을 같은 트랜잭션에서 처리하고, 잠금·lease·재시도·중복 발송·재배정 후 옛 초대 취소를 검증한다. 현재 답변 이메일 큐는 보존하며 새 업무 흐름과 연결한다.
9. **질문 개인정보 처리 기준을 구현한다.** 외부 모델 전송 전 개인정보 탐지·마스킹, 원문·정제본의 저장 범위, 보관기간·삭제·백업 복구 정책을 정한다. 로그·관리자 화면·이메일에서 원문과 토큰 노출 범위를 점검한다.
10. **운영 환경을 확인한다.** 로컬·Railway DB migration 상태와 재시작 후 데이터 유지, OpenAI·메일 장애 복구, 도메인·프록시·쿠키 설정을 확인한다. health 200만으로 DB 정상 판정을 하지 않는다. 정식 공개 전 Vite preview 서버 전환과 배포 복구 절차를 완료한다.

## P3 — 문서와 통합 완료 판정

11. README, `docs/future-work.md`, 환경변수·배포 안내를 현재 동작에 맞춰 갱신한다. 기존 완료 체크는 실제 회귀 검증 후에만 변경한다.
12. 기획서 13장의 MVP 시나리오를 FO → API → DB → BO → 이메일 통합 테스트와 대조한다. 소유권, 동시 배정, 만료·퇴사, 실패·재시작, 모바일 화면을 포함한다.

## 매 작업 완료 기준

- 변경 전 대상 데이터의 식별자·건수·핵심 상태를 기록하고, 변경 후 같은 값을 비교한다. 스키마 변경에는 migration과 기존 데이터 이관·롤백 검토를 포함한다.
- 해당 기능의 성공·거절·재시도 경로를 테스트하고, 관련 타입 검사·lint·빌드 중 적용 가능한 검사를 통과시킨다.
- 테스트가 실행 환경 때문에 중단되면 미검증으로 표시하고 다음 단계의 의존 작업은 완료 처리하지 않는다.
- 구현 파일, 검증 명령과 결과, 남은 위험을 작업 기록에 남긴다.
